# church-calendar (TypeScript) — architecture and parity contract

This package is a TypeScript rewrite of two Ruby projects that run together as the
`church-calendar-api` service (public image `sourceandsummit/church-calendar-api:2.7.0`):

| Ruby project (Lumen-de-Lumine fork) | Role | TS location |
|---|---|---|
| `calendarium-romanum` (fork v2.1.0, `713ebbb`) | liturgical calendar computation library | `src/core/` |
| `church-calendar-api` (fork v2.7.0, `e1ca5c4`) | Grape JSON API + Roda web UI on top of the library | `src/api/` (facade, config, serializers, search), `src/http/` (router + adapters) |

`scripts/sync-data.mjs` expects read-only clones of both forks next to this repository, at
`../church-calendar-api` and `../calendarium-romanum` (override with `CHURCH_CALENDAR_API_DIR` and
`CALENDARIUM_ROMANUM_DIR`).

## Goals, in priority order

1. **Behavioural parity with the Ruby 2.7.0 API.** For every route, the JSON body (parsed) must
   equal what the Ruby service returns. Byte-for-byte equality of the JSON text (three Oj formatting shapes, see docs/BASELINE.md) is the target
   (same key order, same number formatting), but parsed-equality is the pass/fail criterion of the
   conformance suite in `test/conformance/`. Baseline fixtures captured from the Ruby service
   live in `test/fixtures/baseline/` (see its README for the manifest and capture method).
2. **Zero runtime dependencies.** The library must run in Node >= 22, in a browser bundle
   (e.g. webpack 5), and in AWS Lambda. Sanctorale data files and locale strings are
   embedded as generated TypeScript modules under `src/data/` (regenerated by `scripts/sync-data.mjs`
   from the Ruby repos; never hand-edit the generated files).
3. **Embeddable.** `src/http/` exposes a framework-agnostic `handle(request) -> response` router plus
   thin adapters: Node `http`, Express/Nest middleware, AWS Lambda (API Gateway v2 / Function URL),
   and WHATWG `fetch` (`Request -> Response`). A NestJS or Express API can mount it; a Lambda can wrap it; a
   container can run `bin/server.mjs`.
4. **Faithful port, not a redesign.** Keep the Ruby structure and names (translated to TS
   conventions) so a reader can diff against the Ruby source. Put a comment `// ruby: <file>#<method>`
   at the top of each ported unit. Do not "improve" liturgical logic in the port: known Ruby
   quirks are reproduced and documented in `docs/QUIRKS.md` so
   they can be fixed later as deliberate, tracked behaviour changes.

## Package layout

```
church-calendar/
  package.json            ESM ("type": "module"), exports ".", "./core", "./api", "./http"
  tsconfig.json           NodeNext; relative imports MUST use the ".js" extension
  tsconfig.build.json     emits dist/ from src/ only
  jest.config.mjs         @swc/jest, ESM; run with `npm test`
  src/
    index.ts              re-exports core + api + http
    core/                 port of calendarium-romanum (see "Core API")
    data/                 GENERATED: sanctorale .txt contents + locale tables (+ calendars config)
    api/                  port of church-calendar-api lib/ + apps/api (facade, repository, entities, search)
    http/                 router (routes, validation, errors, headers) + adapters
  scripts/
    sync-data.mjs         regenerates src/data/* from ../calendarium-romanum and ../church-calendar-api
    capture-baseline.mjs  captures fixtures from a running Ruby service (e.g. the Docker image)
  test/
    helpers/              fixture loader etc.
    core/  api/  http/    unit tests (ported from the Ruby specs + new characterization tests)
    conformance/          golden tests against test/fixtures/baseline
    fixtures/baseline/    captured JSON fixtures (gzipped) + README.md manifest
  bin/server.mjs          standalone Node HTTP server (PORT env, default 9292)
  lambda/handler.mjs      AWS Lambda entry
  docs/                   ARCHITECTURE.md (this), BASELINE.md, QUIRKS.md
```

Conventions: `strict` TypeScript, no `any` in exported signatures, no runtime deps, no `Date`
objects inside `src/core` and `src/api` (use `CalDate`, below), immutability by default, named
exports only, one class/module per file mirroring the Ruby file names in snake_case ->
kebab-case (`sanctorale_loader.rb` -> `sanctorale-loader.ts`).

## Core API (`src/core`) — the contract the api layer codes against

// dates
export class CalDate {                 // immutable proleptic Gregorian date, no time zone
  constructor(year: number, month: number, day: number);   // throws RangeError on invalid dates
  static fromISO(s: string): CalDate;                     // 'YYYY-MM-DD'
  static fromDayNumber(n: number): CalDate; get dayNumber(): number; // days since 1970-01-01
  static today(): CalDate;                                // UTC calendar date (the Ruby service runs in UTC)
  readonly year: number; readonly month: number; readonly day: number;
  get wday(): number;                                     // 0 = Sunday .. 6 = Saturday  (Ruby Date#wday)
  get cwday(): number;                                    // 1 = Monday .. 7 = Sunday    (Ruby Date#cwday)
  addDays(n: number): CalDate; succ(): CalDate; diffDays(other: CalDate): number; // this - other
  compare(other: CalDate): -1 | 0 | 1; equals(other: CalDate): boolean;
  isBefore/isAfter/isOnOrBefore/isOnOrAfter(other): boolean;
  isSunday(): boolean; isSaturday(): boolean; isMonday(): boolean; isLeapYear(): boolean;

## API layer (`src/api`)

- `calendars.ts` — the `config/calendars.yml` content as a typed object (generated into `src/data/calendars.ts`
  by `sync-data.mjs`, with YAML anchors/merges already resolved; key order preserved because `/calendars` returns the keys in file order).
- `CalendarRepository` — `keys()`, `has(key)`, `get(key): CalendarFacade` (build PerpetualCalendar from layered packaged data + temporale options), `metadata`.
- `CalendarFacade` — `day(date)` (vespers: true, vigils: true — as of 2.7.0), `daysOfMonth(y, m)`, `daysOfYear(y)`, `daysBetween(a, b)`,
  `today()`, `searchTitle(q, start, end)` incl. `spellOutOrdinals` (needs an English number-to-words: port `ordinalize_full` for 1..99 at least; the Ruby regex only rewrites the FIRST ordinal), `year(y)`.
- `entities.ts` — `serializeDay(day, locale)` / `serializeCelebration(c, locale)` producing plain objects with EXACT key order:
  Day: `date, season, season_week, cycle, cycle_sunday, cycle_ferial, celebrations, vespers, weekday`;
  Celebration: `title, colour, rank, rank_num, id` where `rank = shortDesc ?? desc` (localized), `rank_num = priority`, `id = symbol ?? null`.
- `dates.ts` — `parseDateHeader(value)` (RFC 1123 / RFC 850 / asctime, else error) and `parseDateParam(value)` reproducing a subset of Ruby
  `Date.parse`: `YYYY-MM-DD`, `YYYY-MM-DDTHH:MM:SS(.sss)Z` (time ignored), `YYYY/M/D`, `YYYYMMDD`, RFC 1123/850/asctime, `D Mon YYYY`, `Mon D YYYY`.
  Invalid -> the Grape error message the Ruby app produces for that parameter.
- `errors.ts` — `ApiError(status, message)`; JSON body is always `{"error": "<message>"}`.

## HTTP layer (`src/http`)

`createHandler(options?) => (req: HttpRequest) => HttpResponse` (synchronous; safe to `await`) where
`HttpRequest = { method, path, query: Record<string, QueryValue>, headers: Record<string, string> }` (`QueryValue` as Rack parses a parameter) and
`HttpResponse = { status, headers: Record<string,string>, body: string }`. Routes and semantics (from `apps/api/v0/controllers/api_v0.rb`, `apps/web/controllers/web.rb`, `config.ru`):

- `GET /api/v0/:lang/calendars` -> string[] of calendar ids (config order)
- `GET /api/v0/:lang/calendars/:cal` -> `{ system: { promulgated: 1969, effective_since: 1970, desc }, sanctorale: { title, language } }`
- `GET /api/v0/:lang/calendars/:cal/(yesterday|today|tomorrow)` (honours the `Date` request header)
- `GET /api/v0/:lang/calendars/:cal/search?date=` -> `[Day]`; `?q=&startDate=&endDate=` -> `Day[]` (q may be empty/absent)
- `GET /api/v0/:lang/calendars/:cal/:year` -> `{ lectionary, ferial_lectionary }`; `/:year/:month` -> `Day[]`; `/:year/:month/:day` -> `Day`
- `GET /api/v0/:lang/(yesterday|today|tomorrow|:year|:year/:month|:year/:month/:day)` -> 301 to the `default` calendar
- Validation errors -> 400 `{"error": "..."}` with the exact Grape messages (see fixtures `errors/*`); unknown `/api/*` route -> 404 with the Grape body from the fixtures.
- Every response: `Cache-Control: max-age=3600`; `/api/*` and `/swagger.yml` GET get `Access-Control-Allow-Origin: *` (rack-cors) — copy the exact CORS header set from the fixtures.
- Web UI: `GET /` (200 HTML, used as the readiness probe), `/browse`, `/browse/:cal`, `/browse/:cal/:year(/:month)`, `/api-doc`, `/about`, `/swagger.yml`, `/style.css`.
  Port the HTML minimally (server-rendered strings, same information; exact markup parity NOT required).
- Adapters: `adapters/node.ts` (`http.createServer`), `adapters/express.ts` (`(req,res,next)`), `adapters/lambda.ts` (APIGatewayProxyEventV2 / Function URL), `adapters/fetch.ts`.

## Testing

- `npm test` runs everything (jest, @swc/jest, ESM). Unit tests go next to the layer they test under `test/`.
- Port the Ruby specs that are still valid: `calendarium-romanum/spec/*_spec.rb` (rspec) and `calendar/spec/*_spec.rb` (minitest, rack-test). Where the
  Ruby spec is stale (the fork's own suite has 3 failures + 2 errors against 2.7.0, see docs/BASELINE.md) the fixture wins.
- Conformance tests (`test/conformance/`) load `test/fixtures/baseline/**` and compare parsed JSON; on mismatch print a per-date diff
  (date, field, expected, actual) so regressions are readable.
